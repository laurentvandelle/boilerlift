# Deploy plans with reads only, then applies the plan

`deploy` is split into `planDeploy`, which only reads (the workflow list, the API spec, one `GET` per workflow to update, the tag list when a workflow would be created) and decides each workflow's action, and `applyPlan`, which runs the writes. `deploy --dry-run` stops after the plan, so the preview is exactly what a real deploy would do, not a second code path that can drift from it; and a real deploy now does every read before its first write, so an unreachable instance or a rejected key found while reading stops it before anything changes. Rejected: a `dryRun` flag threaded through `deploy()` (every write would need its own guard, and a missed one writes during a preview), a fake read-only client (it would have to invent answers to writes, so the preview would show made-up ids and could not see what the instance refuses), and a saved plan file applied later (the instance can change in between, and the file would need a format and a staleness check). What a plan cannot show is a write that n8n rejects; the dry run says so.
