# Architecture

Operational rules for agents live in `AGENTS.md`. This file is background.

## Intent

Boilerlift is a command-line tool written in TypeScript and published to npm. It reads and validates n8n workflows kept as typed `.workflow.ts` files (an n8n export passed to `defineWorkflow`) or `.json` exports, and delivers them to the user's n8n instance. n8n node definitions are not part of this repository. The instances are declared as named targets in `boilerlift.config.ts` at the project root. The CLI has `help`, `version`, `init` (writes a ready-to-use project from `templates/project/`, which the build copies into `dist/`, never overwriting a file), `ping` (checks the instance connection of a target), `status`, `deploy` (delivers the workflows folder of a target to its instance as drafts, or shows its plan with `--dry-run`), `publish` (makes deployed drafts the published version, after a confirmation), `clean` (archives the workflows removed from the project, after a confirmation) and `creds sync` (writes the credentials of the instance of a target to `credentials/<target>.ts`, and reports the ones its workflows miss). `ping` and `deploy` run on the one declared target, the one `--target` names, or every one with `--all`.

## Modules

- `src/bin.ts` — the executable behind the `lift` and `boilerlift` commands (`bin` in `package.json`). Awaits `runCli` with `process.argv` and the context of the process, then writes the result. An error that escapes a command is printed with its stack, exit 1.
- `src/cli/node-context.ts` — builds the `CommandContext` of the real process: the Boilerlift version, the import of `./boilerlift.config.ts` (after the variables of `./.env` are put into `process.env`), the Node.js version, `fetch`, and the readers of folders, workflow files and the lock file. `src/cli/cli.model.ts` documents each field.
- `src/index.ts` — the package entry point, imported by workflow files and `boilerlift.config.ts` as `'boilerlift'`. Exports `defineWorkflow` and the workflow types (`Workflow`, `WorkflowNode`, `WorkflowConnection`, `WorkflowConnections`), and `credential`, `defineCredentials` and their types (`CredentialLists`, which each generated `credentials/<target>.ts` augments), from `core/compile/`, and `defineConfig` with its types (`BoilerliftConfig`, `TargetConfig`) from `core/config/`.
- `src/cli/` — the CLI: `run-cli.ts` (dispatch), `registry.ts` (the list of commands), `cli.model.ts` (contracts), `define-command.ts` (builds a command from its layers: help, options, needs, prepare, modes and default, render), `targets-need.ts` (resolves the `'targets'` need: the targets `--target` / `--all` select, each with its n8n client), `targets.render.ts` (the output of a command over its targets: one target as is, `--all` as one block per target and a recap, a config error with the available targets) and `commands/<name>/`, one folder per command (a command of two words, `creds sync`, in `commands/creds-sync/`): `<name>.command.ts` declares the command and calls `core/`, `<name>.render.ts` turns the result into the text the user reads. Commands are async: `run` returns `Promise<CliResult>`.
- `src/core/` — the work behind the commands, one folder per concern:
  - `compile/` reads and validates workflow files: `defineWorkflow` and its types for the editor, and a pure loader that checks each export's shape, nodes, connections and stable name before deploy.
  - `deliver/` is deploy: `plan-deploy.ts` reads the instance and decides each workflow's action (also behind `deploy --dry-run`), `resolve-credentials.ts` replaces each `credential()` marker with the `{ id, name }` of the list of the target, checked against the credentials of the instance, `apply-plan.ts` runs the writes, `deploy-failure.ts` says which failures stop the run and with which exit code, `lock-file.ts` reads and writes `boilerlift.lock.json`, the record of the n8n id of each stable name per instance, by which deploy finds its workflows, and `shared-entries.ts` finds targets on one instance whose folders hold the same stable name.
  - `status/` is status: `status.ts` reads, with GET calls only, where each workflow of a target stands on its instance (missing, archived, differs from n8n, draft not yet published, up to date, removed from the project, or not in the project), from the lock file, the comparison of `deliver/normalize.ts` and the draft and published version ids of n8n.
  - `publish/` is publish: `publish.ts` plans from the reads of `status/` which workflows to publish, then publishes each draft through the `N8nClient` port.
  - `clean/` is clean: `clean.ts` reads, with GET calls only, the workflows the lock file records but no workflow file of any target on the instance still names, then archives them through the `N8nClient` port and drops their entries with the lock remover of `deliver/lock-file.ts`.
  - `credentials/` is creds sync: `sync-credentials.ts` lists the credentials of the instance of a target, gives each one its key, writes `credentials/<target>.ts`, and reports the `credential()` keys of its workflows that the list lacks. `compile/credential.ts` holds `credential()`, `defineCredentials` and the scan of markers that `deploy` also uses; `compile/credential-lists.ts` reads the generated lists, for both commands.
  - `connection/` is ping: the checks behind `lift ping`.
  - Shared folders: `config/` (checks the targets of `boilerlift.config.ts`, selects the ones a command runs on, and checks each one has an API key), `n8n/` (the `N8nClient` port, the id guards and what Boilerlift relies on in the public API) and `common/` (the exit codes of every command, `isRecord`, and the `Result` type of expected failures).
- `src/services/` — the adapters that reach the outside world, behind the ports of `core/`. Only `cli/targets-need.ts` uses them, for the commands that need targets:
  - `http/` is the HTTP transport: `getRequest`, `postRequest`, `putRequest` and `deleteRequest` with headers, a JSON body and a reader for the answer, a timeout, and network errors described for a person. It knows no service.
  - `n8n/` implements the `N8nClient` port by calling `http/` directly for each endpoint: the API key, the URLs and paging of the public API, and the parsers that check every body once.
- `debug/` — a separate npm package that depends on `file:../dist` and runs the built `dist/bin.js`, used to try the CLI as a user would.

## Boundaries

- `cli` may import `core`. Only `cli/targets-need.ts` imports `services`, and `services` may import `core`. `core` imports neither `cli` nor `services`.
- In `services/`, `http/` imports only `core/common/`; `n8n/` may import `http/`, `core/n8n/`, `core/config/` and `core/common/`.
- `deliver` may import `compile`. `credentials` may import `compile`, `config` and `n8n`. `compile` never imports `deliver`, `credentials`, `n8n` or `connection`. Shared `core/` folders import neither stage. `deliver` and `connection` do not import each other.
- A command imports only its own folder, the CLI contracts and `core`. Never another command.
- Commands, `services/` and `core/` get the outside world through their parameters (the injected `CommandContext`, the `N8nClient` port, an injected `fetch`) and return their output. `node-context.ts` and `bin.ts` do the I/O.
- `debug/` sees only the published surface in `dist/`, never `src/`.

`npm run lint:check` enforces the `src/` rules: `eslint-plugin-boundaries` the import directions, and the hidden-dependency bans of `eslint.config.mts` the I/O rule. No check enforces the `debug/` rule.

## Runtime

`npm run build` compiles `src/` with `tsc` (module `node20`, target `ES2024`, CommonJS output since `package.json` has no `"type"`) into `dist/`, emitting `.d.ts` and source maps. Imports keep the `#src/` alias in `dist/`: Node.js resolves it at runtime through the `imports` field of `package.json` (`#src/*` → `./dist/*.js`), so no rewrite step runs. `package.json` points `main` at `dist/index.js` and `types` at `dist/index.d.ts`. The minimum runtime is Node.js 22.18 (`engines` in `package.json`); development uses Node.js 24 (`.nvmrc`), the only version CI tests. `npm start` builds, then runs `debug/main.ts` with `node` (Node.js 22.18 and later strip TypeScript types natively). With no argument, `debug/main.ts` runs a real `lift deploy` of `debug/workflows` to the `dev` target in `debug/boilerlift.config.ts`, whose url and API key come from `debug/.env`, so `npm start` writes to that instance.

## Out of scope

No runtime dependencies, no bundler, no ESM dual build.
